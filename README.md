# Git AutoPick

自動化處理多專案 `git cherry-pick` 的批次工具，提供直覺的 Web 介面與即時日誌串流，並具備完整的防護與失敗復原機制。

## 主要功能

*   **Worker Pool 佇列式併發處理**：支援自訂並發數量（Concurrency 1~10，預設 3），多專案平行處理 `switch/pull/fetch/cherry-pick/push`，顯著縮短批次處理總耗時。
*   **多專案批次選取**：透過現代版目錄選取器（Windows 原生對話框），一鍵選取多個本地專案進行批次執行。
*   **自動化復原 (Rollback)**：
    *   `switch/pull/fetch` 失敗：直接跳過該專案，避免副作用。
    *   `cherry-pick` 衝突：自動執行 `--abort` 清理狀態。
    *   `push` 失敗：自動執行 `reset --hard HEAD~1` 還原 commit。
*   **PR 模式（GitHub）**：推送至工作分支並開立 Pull Request。全新分支自基準分支切出、既有分支獨立更新進度；完成後自動切回執行前的分支。可選擇**建立後自動合併**，讓「分支 → PR → 合併」的流程全自動跑完。詳見下方「PR 模式」。
*   **高風險分支確認閘門**：工作分支命中主線名單（`main`、`release/*` 等）時，直推前需明確確認並列出實際受影響的專案清單。**保留直推能力**——防的是誤觸，不是直推本身。
*   **不使用強制推送**：任何路徑皆不產生 `--force`、`--force-with-lease` 或 `-f`。每一條失敗路徑都有不依賴強制推送的回退方式。
*   **防呆與去重防護**：執行前檢查工作目錄是否乾淨，有未提交變更即略過該專案；自動過濾重複目錄避免 Git lock 競爭；自動識別已存在的 commit；支援「模擬模式 (Dry-Run)」預演執行，不影響本地代碼。
*   **即時日誌串流分流**：Web 端基於 SSE 即時分組顯示各專案執行進度與終端機日誌，免刷新頁面且多專案平行執行時畫面不混亂。

## 應用技術

*   **後端 (Backend)**：Node.js (`Express`) + `child_process` (與 Git CLI 互動) + Worker Pool 併發調度
*   **前端 (Frontend)**：HTML / CSS / Vanilla JS (無框架)
*   **通訊技術**：Server-Sent Events (SSE) 單向即時資料流與多專案日誌分流
*   **系統整合**：PowerShell 腳本 (呼叫 WPF `OpenFileDialog` 實現現代化目錄選取)
*   **UI 設計**：基於 OKLCH 色彩空間的 Dark Luxury 工具型介面

## 執行方式

環境需求：必須安裝 **Node.js (v18+)** 與 **Git**。

### 方式一：一鍵啟動（推薦）
在專案根目錄，直接雙擊執行 `start.bat`。
*(批次檔會自動安裝依賴、啟動後端伺服器，並開啟瀏覽器)*

### 方式二：手動啟動
若需要透過終端機執行：

1.  **安裝依賴**
    ```bash
    npm install
    ```
2.  **啟動 Web 伺服器**
    ```bash
    npm run web
    ```
3.  **開啟網頁**
    在瀏覽器輸入網址：`http://localhost:3131`

## PR 模式

於 Web 介面開啟「PR 模式」後，流程改為推送至工作分支並開立 Pull Request，適用平台為 GitHub。

### 分支就位規則

工作分支依本地與遠端的存在狀態決定就位方式：

| 本地 | 遠端 | 行為 |
|------|------|------|
| ✗ | ✗ | 自 `<推送 Remote>/<合併目標分支>` 切出新分支 |
| ✗ | ✓ | 切換至該分支並建立追蹤 |
| ✓ | ✓ | 切換後以 `--ff-only` 拉取進度（分岔時中止，不產生合併提交） |
| ✓ | ✗ | 切換後略過拉取 |

### PR 建立方式

分為兩種軌道，介面會顯示目前生效者：

*   **開單連結（零依賴，預設）**：推送完成後產生預填 base 與 compare 的 GitHub 開單連結，點擊即進入建立頁面。
*   **自動建立（需 `gh` CLI）**：偵測到已安裝並完成 `gh auth login` 時，自動建立 PR；該分支已有開啟中的 PR 則取回既有網址。

安裝 `gh` 為選配，未安裝不影響其餘功能。

### 自動合併

適用情境：**主線分支僅禁止直推、不要求審核核准**——此時 PR 是流程要求而非審查關卡，整段流程可全自動完成。

是否自動合併由「建立後自動合併」開關決定，**預設關閉**。三種組合的流程終點如下，介面會即時顯示目前落在哪一種：

| `gh` CLI | 自動合併 | 流程終點 |
|---------|---------|---------|
| 未安裝 | —（停用） | 推送完成，PR 需自行至 GitHub 建立與合併 |
| 已安裝 | 關 | PR 已建立並停在待合併，可自行至 GitHub 按下 Merge |
| 已安裝 | 開 | PR 建立後直接合併，無需人工介入 |

開啟時可選擇合併方式（Squash／Merge commit／Rebase）與是否刪除工作分支。合併在切回原分支之後執行，因為刪除分支無法在該分支被檢出時進行。

全程不涉及核准動作。GitHub 不允許核准自己的 PR，該限制在 API 層級同樣成立，因此若目標分支**要求審核核准**，自動合併會失敗並明確說明原因，PR 仍保留供人工接手。

此選項需要 `gh` CLI；未偵測到時開關為停用狀態。

### 失敗時的回退

| 階段 | 遠端狀態 | 回退方式 |
|------|---------|---------|
| cherry-pick 失敗 | 未變更 | 中止套用、切回原分支、刪除本次新建的臨時分支 |
| push 失敗 | 未變更 | 本地重置至執行前的提交、切回原分支 |
| PR 建立失敗 | 已含該提交 | 不自動回退；提供開單連結，並於日誌輸出 `git revert` 指令 |
| 自動合併失敗 | 已含該提交、PR 已建立 | 不自動回退；保留 PR 供人工合併，並說明失敗原因 |

推送成功後的內容不會被自動撤銷——撤銷需要強制推送，屬全域禁止項。需要退回時以 `git revert` 產生反向提交，該方式不需強制推送。

### 模擬模式的行為

模擬模式下變更型指令僅顯示不執行，唯讀查詢（分支是否存在、目前分支、工作區狀態）仍實際執行，因此預覽的流程分流與實際執行一致。
